# 未来事件任务：两类来源的定义、边界与需求说明

> 适用版本 0.3.1 及以上。本文只定义"什么算哪一类、谁负责生成、各自边界"，
> 具体字段与接口见 [承诺任务](promise.md) 与宿主 `core/cron/manager.py`。

## 0. 结论先行

你的两分法是成立的：**未来事件任务按"义务由谁产生"分成两类**，而不是按
"到点做什么"分。但有三处需要修正，否则落地会走偏。

| # | 你的表述 | 实际情况 | 修正 |
| --- | --- | --- | --- |
| 1 | 第一类支持一次性、周期性、时间段内一次性三种形态 | 宿主 `future_task` 只有 `run_at`（一次性）和 `cron_expression`（周期）两条路；`run_once=true` 时 cron 会被强制置空 | **宿主做不了"时间段内一次性"**。这个形态要么在创建前把窗口收敛成一个具体时刻，要么交给 LivingEmotion 的档位 |
| 2 | 第二类由 Bot 承诺生成 | 成立。但 LivingEmotion 的 `promises` 表**没有来源字段** | 现在两类在库里长得一模一样，无法区分、无法分别统计、无法分别去重 |
| 3 | 两类互不混淆 | 现状是 LivingEmotion 同时接了两类：用户说"2 分钟后提醒我"，模型也走同一套承诺标记 | 需要**显式归类**，否则"用户指令"会被当成"Bot 承诺"统计和兑现 |

一句话：**分类标准不是"谁在什么时候说"，而是"这件事没做，是谁欠的"。**

## 1. 两类任务对照

| 维度 | A 类：用户发起 | B 类：Bot 承诺 |
| --- | --- | --- |
| 触发主体 | 用户 | Bot 自己 |
| 义务来源 | 用户的明确指令（"提醒我""叫我""每天八点"） | Bot 在回复里说过的话（"晚点发你""一会儿拍给你"） |
| 生成方式 | 模型调用 `future_task` 工具（工具调用） | 回复末尾的注释标记，装饰阶段剔除，消息真正发出后落库 |
| 存储 | `data_v4.db` → `cron_jobs`，`job_type=active_agent` | `livingemotion.sqlite3` → `promises` |
| 形态 | 一次性（`run_at`）、周期（`cron`） | 一次性：精确延后（`2分钟`）或档位窗口（`今晚`=20:00–22:59 内随机） |
| 到期做什么 | 用 `note` 唤醒主 agent，走完整对话（可调工具、可生成） | 只生成一句话并发出去，不走主 agent |
| 可取消 | `action=delete` / `edit` | 聊天里说"不用了"，或加 `<!--promise-cancel:...-->` |
| 可改时间 | `action=edit` | "早点给我" → 提前到 20 秒后，单日上限 3 次 |
| 跨重启 | 是（APScheduler + DB） | 是（`scheduled` 状态，tick 15 秒扫） |
| 失败语义 | 记 `last_error`，无重试队列 | 重试 3 次（每次退避 5 分钟），夜间被拦不计次 |
| 额度 | 不占主动行为额度 | 不占主动行为额度（独立 `promise` 池） |
| 写记忆 | 不写（它是日程，不是人格经历） | 必须写（否则追问"你刚才说什么"接不上） |
| 对用户可见 | 通常可见（用户自己提的） | 不可见标记；面板有卡片 |

## 2. A 类：用户发起的未来任务

### 定义

用户在对话里明确提出"到某个时间做某件事"，义务来自用户。Bot 只是执行器。

### 生成方式

不是注释标记，是**一次工具调用**：

```json
{"action": "create", "name": "提醒关火", "note": "提醒他关掉还在烧的水",
 "run_at": "2026-11-16T01:30:00+08:00", "run_once": true}
```

任务自动绑定 `session`（`unified_msg_origin`）与 `sender_id`，`origin="tool"`。
到期时用 `note` 唤醒主 agent——注意这会**再调一次模型**，所以 `note` 要写成
给"未来的自己"的指令，而不是给用户看的文案。

### 三种形态的落点

| 形态 | 宿主怎么写 | 备注 |
| --- | --- | --- |
| 一次性（精确时刻） | `run_at` + `run_once=true` | 支持到秒 |
| 周期性 | `cron_expression`（如 `0 8 * * *`） | 支持 `mon-fri` 这类名字，别用数字区间 |
| 时间段内一次性 | **宿主没有这个参数** | 必须在创建时收敛：要么由模型挑一个具体时刻写进 `run_at`，要么交给 LivingEmotion 的档位（`今晚`/`一会儿`） |

### 边界

- **不支持"模糊到没有时刻"**：`note` 必填、`run_at` 必填（一次性时）。"有空提醒我"不是 A 类任务。
- **不写进人格记忆**：A 类是日程，不属于"经历"，不参与情绪/关系计算。
- **不占主动行为额度**：用户点名的，不该挤掉 Bot 自己想说话的次数。
- **周期任务只能走 A 类**：LivingEmotion 的承诺状态机没有"下次触发"概念，写进去就是死账。

## 3. B 类：Bot 承诺的未来任务

### 定义

Bot 在回复里自己应下一件"这一轮不做、稍后做"的事。义务来自它自己说过的话，
**用户没有要求它设定时器**。这是"人格一致性"问题，不是"日程管理"问题。

### 生成方式

四步，缺一不可：

1. 模型在回复最后一行写 `<!--promise:档位:这件事做什么-->`（用户看不到）
2. 装饰阶段把标记从正文抠掉（只就地清，跨组件搬运会导致同一句发两遍）
3. 消息真正提交给宿主之后才落库（没发出去就不建，避免幽灵任务）
4. 状态机接管：`scheduled → running → sent`，失败可重试

### 形态

只有一次性，但有两套时间语义：

| 写法 | 落点 |
| --- | --- |
| `2分钟` `90秒` `1小时` `半小时` | 确切延后，用户说几分钟就是几分钟 |
| `马上` / `一会儿` / `待会` / `今晚` / `明天` / `过几天` | 区间内随机（`今晚`=20:00–22:59） |

**没有周期**。Bot 不该承诺"我每天提醒你喝水"——那句话应该由 A 类承担，
或者干脆不说。

### 边界

- **必须可撤回**：只有一条时"不用了"直接取消；多条时先列编号，不猜。
- **必须可提前**："现在就发" → 20 秒后触发，单日 3 次上限。
- **必须去重**：同 `(会话, 归一化描述)` 只保留一条；刚发过的 10 分钟内不再建。
- **必须写记忆**：兑现的那句话要落 `documents`，否则用户追问时它一脸茫然。
- **夜间不拦**：作息表只管"自己找话说"，不管"答应了要给的"。
- **会话消失就作废**：对方删号/换实例，直接 `cancelled`，不每 15 秒空转。
- **兑现不占主动额度**：见上表。

## 4. 判别规则

给模型和人都能用的四条：

| 情形 | 归类 | 理由 |
| --- | --- | --- |
| 用户："十分钟后提醒我关火" | **A** | "提醒我"是指令，义务在用户 |
| 用户："每天八点叫我起床" | **A**，且只能 A | B 不支持周期 |
| 用户闲聊，Bot 回："晚点拍给你看" | **B** | 用户没要求定时，是 Bot 自己应下的 |
| Bot 主动："我明天提醒你" | **B** | 义务由 Bot 单方面产生 |
| 用户："你明天记得提醒我" | **A** | 有明确指令，别降级成 B |

一条快速判据：**这句话里有没有"提醒我/叫我/到点告诉我"这类祈使句。**
有 → A；没有，但 Bot 说了"稍后/晚点/一会儿" → B。

## 5. 交叉与冲突

目前已知四个真实冲突点：

1. **双写**：同一轮里模型既调 `future_task` 又写承诺标记，用户会收到两条。
2. **A 类走错通道**：用户明确要定时，结果记成 B，于是没有 `list`/`edit`，
   用户想改时间只能靠聊天里的"早点给我"。
3. **周期写进 B**：`<!--promise:明天:每天提醒他喝水-->` 只会触发一次。
4. **主动聊天撞车**：宿主 `cron_jobs` 里那条"主动找主人聊话题"（10:30/15:30/20:30）
   与 LivingEmotion 的随机主动行为（90–240 分钟、冷却 2 小时）会各说一次。

### 需求：写入前去重

| 检查 | 动作 |
| --- | --- |
| 同 session + 归一化 `note` 相同 + `run_at` 相差 < 60 秒，且另一类已有记录 | 丢弃后写的那条，日志记 `cross_duplicate` |
| B 类请求里出现"每天/每周/每天X点" | 拒绝记账，改为提示走 A 类 |
| A 类请求来自"Bot 自己说"而非用户 | 不允许，A 类必须由用户指令触发 |

## 6. 现状与差距

| 差距 | 位置 | 影响 |
| --- | --- | --- |
| `promises` 无来源字段 | 表结构 18 列，无 `origin` | 两类混在一起，面板无法分开展示，用量无法分别统计 |
| 契约没写"周期不许记账" | `runtime/application.py` 的记账规则 | 模型可能把周期任务写成一次性承诺 |
| 无跨表去重 | `promise_store.create` 只查本表 | 双写无拦截 |
| A 类同时被两套接住 | `future_task` 与承诺标记并存 | 同一句用户指令可能生成两条 |

### 建议的最小改动

1. `promises` 增 `origin TEXT NOT NULL DEFAULT 'bot_promised'`，
   标记值 `user_requested` / `bot_promised`；契约里加一个可选来源段
   （如 `<!--promise:2分钟:提醒他关火|user-->`），缺省按 `bot_promised`。
2. 契约加一条硬约束：**周期任务不记账**，并在检测到"每天/每周"时直接不写。
3. `create` 前查一次 `cron_jobs`（同 session + 同 note + `run_at` ±60 秒），命中即丢弃。
4. 面板按来源分两栏：「你让它记的」与「它自己答应的」。
5. 关掉 native 的"主动找主人聊话题"，让主动聊天只由一个子系统负责。

## 7. 验收标准

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 用户说"十分钟后提醒我关火" | `cron_jobs` 多一条 `run_at` 任务，`promises` **不新增** |
| 2 | 用户闲聊，Bot 说"晚点发你" | `promises` 新增一条 `bot_promised`，`cron_jobs` 不新增 |
| 3 | 用户说"每天八点叫我" | 只建 cron 任务；若模型写了承诺标记，落库结果为 `rejected:recurring_not_supported` |
| 4 | 同一轮双写 | 只保留一条，另一条 `cross_duplicate` |
| 5 | 承诺到点 | 15 秒内发出，`last_error` 为空，`documents` 有对应 `bot_action` |
| 6 | 用户在面板查看 | 两类分栏显示，A 类可跳转到任务管理，B 类只读 |

---

**一句话总结**：A 类是"用户交给 Bot 的日程"，要有唯一的创建入口和可编辑性；
B 类是"Bot 自己欠下的债"，要有状态机、可撤回和记忆留痕。
两者可以共用投递通道，但**不能共用语义**——混在一起，A 类会失去可管理性，
B 类会失去人格一致性。
